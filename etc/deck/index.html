What? - EVM

  • Ethereum VM — the runtime for smart contracts
  • Stack-based, 256-bit word, flat memory
  • Deterministic: same (input, state) → same output
  • Specified in the Yellow Paper and EIPs


Why build a new one in 2026?

Ethereum VM is a simple stack-based VM with flat memory and a 256-bit word size. It is deterministic — same state and same input always produces the same output. State mutations happen in batches: transactions within blocks. The spec lives in the Yellow Paper and EIPs. Why build one? Production implementations are world-class but hostile to newcomers, and none of them — to my knowledge — compile cleanly to Wasm without patching. I wanted something that runs in a browser and shows what is happening under the hood.

Why? - wasm, async, observability

  • Production EVMs (geth, revm, evmone) are hyper-optimized and hard to audit
  • No clean wasm-native, async-friendly implementation existed
  • Target: browser-based tooling — IDEs, light clients, simulations
  • Goal: deep understanding of how EVM works "under the hood"
Multiple reasons to build a new one. Production EVMs are hyper-optimized and hard to get into. No clean Wasm-native async-friendly implementation existed. Target: browser-based tooling. Goal: deep understanding of what happens under the hood.

Why? - WebAssembly

  • Runs in the browser — no backend, no install
  • wasm32-unknown-unknown: no OS, no stdlib
  • Same code runs natively and in the browser
  • Portable simulation at the edge
    • wallets
    • IDEs
    • light clients
WebAssembly is the straightforward path to browser interoperability. Same code runs natively and in the browser. It opens up integration with wallets, IDEs, and light clients.

Why? - async

  • EVM needs external data: storage slots, account code, balances
  • In the browser those fetches are always async (fetch, XHR)
  • Sync EVM will fail to run in the browser (blocking the main thread)
  • Async-first design makes the browser a first-class target
Real-world programs do IO. In a browser context, blocking the main thread is simply not allowed. Async-first and Wasm-friendly are essentially the same requirement looked at from two angles.

Why? - observability

  • Production EVMs are black boxes — input in, output out
  • Solenoid exposes every opcode, stack frame, memory write, storage access
  • Useful for: debugging, education, security auditing, simulation UI
  • Though full traces might be too much data to handle in browser effectively
I wanted to turn EVM from a black box into a glass box — fully observable end-to-end. But observability is on-demand: opcode-level traces are far too much for most use cases. YAEVMI captures and emits them only when asked. This is useful for dev tooling, debugging, education, transaction simulation, and security.

Why? - security

  • February 2025: $1.5B stolen from ByBit — largest crypto hack ever
  • Root cause: malicious transaction looked safe in the UI, but wasn't
  • A browser-native EVM could have simulated the full execution before signing
  • Side effects, storage changes, token transfers — all visible before broadcast

Simulation could have prevented the ByBit hack!

The ByBit hack illustrates the problem: even with multisig, no signer could see what they were actually signing — inputs, not side effects. A simulation tool could fix that. I will be modest and say simulation could have prevented the ByBit hack, rather than YAEVMI specifically. We will see those transactions in the live demo.

How? - overview

  • 📄 Spec — implement the Yellow Paper + EIPs faithfully
  • ⚖️ A/B — compare step-by-step against revm
  • 🔁 Trial & error — run real mainnet blocks, fix what breaks
Three pillars: implement the spec faithfully, A/B test against revm, and run real mainnet blocks until nothing breaks.

How? - spec

  • Yellow Paper is the ground truth — but it's dense and occasionally wrong
  • EIPs override the Paper — and sometimes contradict each other
  • Gas rules have many special cases: SSTORE, CALL, warm/cold access
  • Ethereum GeneralStateTests: ~7000 test cases across all opcodes and EIPs
  • Getting to 99%+ took fixing ~10 subtle bugs — each one a spec rabbit hole
The starting point is a fine-grained spec covering all state transitions and opcodes. I started with the spec and ran A/B tests against revm. If gas accounting and opcode-level traces match on every step, the implementation is correct. Yellow Paper plus EIPs. The tricky part is EIPs layering on top of each other — hunting a bug where one EIP caps gas differently and the numbers just do not match. For correctness, there is the Ethereum general state test suite: thousands of test cases. I reached 99.6% pass rate. The remaining discrepancies were because the suite targets Cancun fork, and there have since been two more forks: Prague and Osaka. It works against mainnet — that is what matters.

How? - A/B against revm

  • The revm trace is the source of truth*
  • Run the same tx through YAEVMI and revm
  • Compare every step: opcode, PC, gas, ...
  • Step mismatch → implementations diverge
  • Gas + Trace + State match → peace of mind
Any mismatch gets investigated. The most common case: a revert not applied correctly, causing a wrong jump condition downstream. When gas accounting and opcode traces match at every step, I call it peace of mind. I reached 1000 consecutive blocks with 100% match against on-chain receipts. That is when I decided it was time to give a talk.

How? - trial & error

  • Replay real mainnet blocks — 10, then 100, then 300, then 1000
  • Each milestone exposed new bugs: EIP-7623, EIP-7702, CREATE2 collision
  • Failed txs go into a queue, get fixed, re-replayed
  • 1000 consecutive blocks, zero failed transactions — the finish line
The hardest bugs came from gas accounting. One bug could take days; the fix was a single line. The subcall gas rule is where I spent the most time. If I see a gas discrepancy of 39, I know it is a subcall. Beyond gas, revert was the other tricky one. You only know at the end of subcall execution whether it succeeds, it can fail any moment, and if it does, you need to undo all sub-call side effects precisely. The spec is not hard — it is the accumulated complexity of years of overlapping changes.

Designing and evolving such complex thing is hard

This is a small excerpt from the Yellow Paper. It is dense, it is occasionally wrong, and the EIPs layer on top of it. Following the spec is the only way through.

Solenoid: async-first design

  • External calls (storage, code) are async trait methods
  • Portable: compiles to wasm32-unknown-unknown
  • Observable: every state transition is inspectable


  // simplified
  async fn execute(&mut self, opcode: u8) -> Result<()> {
      match opcode {
          SLOAD => {
              let key = self.stack.pop()?;
              let val = self.storage.load(key).await?;  // async fetch
              self.stack.push(val)
          }
          // ...
      }
  }
Solenoid's design is simple: everything is async. Need to look up a state slot? Do it inside the opcode handler. Straightforward — but the async overhead adds up.

The async tax

  • Each .await is a yield point — overhead adds up
  • Codegen for deeply nested async is expensive
  • Result: 10–100× slower than revm

But for browser use cases — latency hides the cost:

  • Network round-trips dominate
  • User doesn't notice 10ms vs 100ms
  • Wasm portability is worth the tax
revm executes a transaction in roughly 3 ms. Solenoid took 300 ms. Two orders of magnitude for the same business logic. From a user perspective in the browser, 3 ms versus 300 ms is not visible. But it is surprising and unacceptable for essentially identical logic.

Lessons learned from Solenoid

  • The Yellow Paper has many subtle edge cases
  • Gas accounting is hard (looking at you SSTORE)
  • Debug info is very expensive — allocator round-trips add up fast in a hot loop
  • Async in hot paths is still very expensive
  • Key insight: the VM yields at every .await — what if it didn't?
Gas accounting is the hardest part end-to-end. Debug output in a hot loop gets expensive fast — allocator round-trips add up. Async in hot paths needs to be avoided. That got me thinking: what if instead of the runtime managing yields, I make yield part of the domain model?

YAEVMI: make yield part of the design

  • Solenoid yields to the executor on async fetches
  • YAEVMI returns fetch request, sync execution
  • Execution and fetching are decoupled:
    • opcode handler is sync (no .awaits)
    • executor is async (handles fetches)
    • but deals with "pending" side-effects
In YAEVMI, a yield is a situation where the EVM lacks data. It returns and expects the caller to resolve it. Execution and data fetching are fully decoupled. Handlers are sync — no awaits. The executor is async because it needs to fetch state. This introduces pending side effects, which need careful management. One complexity traded for another — but worth it, as the benchmarks will show.

YAEVMI: model


pub struct Call {...} // from, to, gas, data, value

pub enum HaltReason {...} // out-of-gas, out-of-memory, ...
pub enum CallMode {...} // call, static, delegate, callcode, create, create2
pub enum Fetch {...} // code, nonce, balance, account, block, state

pub enum EvmYield {
    Return(Vec<u8>),
    Revert(Vec<u8>),
    Halt(HaltReason),
    Call(Call, CallMode),
    Fetch(Fetch),
}

pub type EvmResult<T> = std::result::Result<T, EvmYield>
The Result type is T or Yield. The error variant is a yield, not an error. Idiomatic Rust Result, repurposed as Either.

YAEVMI: dispatch


pub fn dispatch<S: State>(
    op: u8,
    evm: &mut Evm,
    ctx: &Context,
    call: &Call,
    state: &mut S) -> EvmResult<()> {
    match op {
        0x00 => basic::stop(evm),
        // ...
        0x31 => chain::balance(evm, ctx, call, state),
        // ...
        0xFF => calls::selfdestruct(evm, ctx, call, state),
        _ => invalid(evm, ctx, call, state),
    }
}
Dispatch is a match on opcode, each routing to its sync handler. Simple and fast.

YAEVMI: BALANCE handler


pub fn balance<S: State>(evm: &mut Evm, state: &mut S) -> EvmResult<()> {
    evm.gas_charge(100)?;
    let [acc] = evm.peek()?;
    let acc: Acc = acc.to();
    let Some(balance) = state.balance(&acc) else {
        return Err(EvmYield::Fetch(Fetch::Balance(acc)));
    };
    if state.warm_acc(&acc) {
        evm.gas_charge(2_500)?;
    }
    evm.push(balance)?;
    Ok(())
}
The BALANCE handler shows the pattern clearly: if no balance for the account, yield. When retried after the fetch resolves, pending state changes are reverted and reapplied cleanly.

YAEVMI: pending state

Opcode handler:

  • stores pending state changes
  • applies them on success
  • reverts them on fetch
One complexity traded for another — but worth it. The handler manages its own pending changes: apply on success, revert on yield, retry after fetch.

YAEVMI: streaming traces

  • Solenoid collected full per-opcode traces in memory → 55GB for Aztec rollup txs
  • yaevmi emits trace events as a stream — consumer decides what to keep
  • Same observable design, zero memory blowup
  • Verified for 5M+ gas transactions with 100k+ steps
Instead of buffering all traces in memory, YAEVMI streams them out. If you do not subscribe, they are not even captured. Zero memory pressure, zero cost when you do not need them.

YAEVMI: streaming

  • Same code works natively and in browser
  • Non-blocking without sync primitives
  • Needs explicit yields to reduce memory pressure
  • 🤔
The challenge: streaming needs to work both natively and in the browser, non-blocking, without sync primitives.

YAEVMI: streaming

  • futures::channel::mpsc FTW!
  • See sieve for more details
The answer is futures::channel::mpsc — a non-blocking channel that works both natively and in the browser. The sieve demo shows it in action. Fifty lines of code.

YAEVMI: results

  • 99%+ of Ethereum GeneralStateTests (Cancun fork) passing
    • not the case for Osaka fork (current one)
  • 1300+ mainnet blocks replayed — zero failed transactions
  • Comparable to revm performance on modern hardware
  • Seamlessly builds for wasm32-unknown-unknown target
    • minor code tweaks were still necessary
99%+ of general state tests passed for Cancun fork. Over 1000 blocks replayed without a single failed transaction. Performance is comparable to production-grade implementations. Wasm is seamlessly supported with minor tweaks for no-std: mostly around time and randomness.
